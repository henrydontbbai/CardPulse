# CardPulse 产品定位与下一阶段方向

## 一句话定位

CardPulse 不再只是“给 4G 模块发一条 AT 短信的脚本”，而是一个 **本地运行的 SIM 短信运维面板 / AT 网关**：

- 能看模块状态
- 能安全收发短信
- 能查看收件箱
- 能做保号任务
- 能通过本地 Web 面板完成日常运维

它的目标不是做公网短信平台，也不是先做复杂驱动，而是先把 **“一张 SIM 在一台本地设备上稳定可控”** 这件事做扎实。

## 当前已验证的现实能力

基于当前 DJI / Baiwang QDC507 模块，这条链路已经被真实验证：

- Windows 主机 + WSL2 + `usbipd`
- Linux `option` 驱动接管 USB 设备
- CardPulse 通过 `/dev/ttyUSB2` 使用 AT 串口
- 可读取 SIM 状态、信号、运营商、IMEI
- 可真实发送短信
- 可真实接收短信
- 可查看短信存储状态、收件箱、单条读取、单条删除
- 本地 Web 控制台可用，默认关闭 Web 发信能力

这说明 CardPulse 的主线已经从“脚本实验”进入到了“可日常操作的本地工具”阶段。

## 当前技术现实

### 1. 现在走的是 AT 路线

当前 CardPulse 的核心接口仍然是 **AT 串口**。  
也就是说，CardPulse 现在依赖操作系统里出现可访问的串口，例如：

- `/dev/ttyUSB*`
- `/dev/ttyACM*`
- `/dev/cu.*`
- Windows `COM*`

当前这块 DJI / Baiwang 模块在现有环境里，真正稳定可用的是：

- WSL/Linux 侧出现 `/dev/ttyUSB2`
- CardPulse 通过这个端口做 AT 命令交互

### 2. Windows 原生直连不是当前主路线

目前这块模块在 Windows 原生侧没有稳定暴露出可直接使用的：

- `COM` 串口
- 标准 Modem 接口
- 可直接复用的 WWAN 控制接口

所以短期内最小可用、成功率最高、风险最低的路线，仍然是：

**Windows 控制机 + WSL2 + Linux 串口驱动 + CardPulse**

### 3. 自己做 Windows 驱动不是当前优先级

理论上可以继续研究 Windows 原生驱动适配，但它不是产品当前最优动作，原因很直接：

- 成本高
- 验证慢
- 设备兼容性不确定
- 很容易把精力从产品功能拉回到底层驱动问题

对当前目标来说，这属于“技术探索项”，不是“主线交付项”。

## 这个产品现在真正解决什么问题

从真实使用角度，CardPulse 现在解决的是：

1. **本地接管一张 SIM**
2. **确认它在线、可发、可收**
3. **避免误操作，降低短信风险**
4. **让日常保号、查信、删信、做测试变得可视化**
5. **让硬件恢复流程尽量可重复**

所以 CardPulse 更像一个：

> 轻量本地 SIM 运维台

而不是：

- 公网短信 SaaS
- 多租户平台
- 云端群发系统
- 需要先做底层驱动工程的大项目

## 目前还不够好的地方

虽然主链路已通，但现在仍然偏“工程可用”，还没完全到“产品顺手”。

### Web 面板还偏调试台

现在 Web 控制台能用，但更像一个面向开发/排障的控制页，还不够像真正的运维产品首页。

还缺少：

- 一个更明确的总览首页
- 更清楚的模块在线 / SIM / 信号 / 存储健康状态卡片
- 新短信 / 存储满 / 端口异常的显著提示
- 更连续的操作反馈和历史感

### 端口恢复仍有手动痕迹

虽然已经有一键恢复脚本，但“设备重插 / 系统重启 / WSL 重新接管”这条链路仍然比较脆弱。

下一步应该继续优化为：

- 启动即检查设备是否在位
- 自动判断 USB 是否已 attach
- 自动确认 `/dev/ttyUSB2` 是否可用
- 页面上直接展示当前连接状态，而不是让用户猜

### 还缺少轻量事件视图

目前能查状态，也能看收件箱，但还没有一个“最近发生了什么”的统一视图。

比如：

- 最近一次保号短信何时发送
- 最近一次发送是否成功
- 最近一次接收到新短信是什么时候
- 最近一次端口恢复是否成功

这类信息一旦集中展示，产品可用性会明显提升。

## 下一阶段推荐优先级

### P0：把 Web 首页做成“日常运维首页”

优先不是加更多底层功能，而是把现有能力组织得更顺手。

建议首页先聚焦 4 个区块：

- 设备在线状态
- SIM / 信号 / 运营商 / IMEI
- 短信存储状态与新短信提示
- 最近发送 / 接收 / 错误事件摘要

这是最能直接提升产品感知价值的一步。

### P1：把连接状态做成显式、可恢复

重点优化“端口连接是否正常”这件事，让它从技术细节变成产品状态：

- 已连接：显示当前 AT 端口
- 已发现设备但端口不可用：提示恢复动作
- WSL 未 attach：给出明确指引
- AT 无响应：给出单独错误态

这一步会直接降低使用门槛。

### P1：加入轻量自动刷新与新短信检测

不是做复杂后台常驻，而是先做轻量、可控的运维增强：

- Web 自动刷新基础状态
- 新短信数量变化提示
- 存储接近满仓告警
- 最近一次异常的醒目展示

### P2：把“保号任务”产品化展示

保号是 CardPulse 的核心业务价值之一，下一步应该把它从配置项提升成可理解的产品视图：

- 上次发送时间
- 下次预计发送时间
- 当前策略是否生效
- 最近一次保号结果

这样用户不需要翻配置和日志，也知道系统是不是在正常工作。

## 当前不建议优先投入的方向

为了保持产品节奏，以下方向暂时不建议放到主线前面：

### 1. Windows 原生驱动项目

可以研究，但不应该压过当前主线。它更像后续兼容性优化，不是现在的核心价值来源。

### 2. 公网开放 Web 面板

当前产品更适合作为本地运维面板。过早公网化会引入认证、权限、安全、审计等一整套复杂度。

### 3. 自动删除短信

风险太高。当前单条确认删除是正确的安全边界。

### 4. 复杂多卡平台化

在单卡链路已经很好用之前，不建议过早扩成多卡调度系统。

## 推荐的产品心智

接下来继续做 CardPulse，最适合的心智不是：

> “把更多 AT 命令堆上去”

而是：

> “把一张本地 SIM 的状态、收发、保号、收件箱和恢复动作，做成一个稳定、顺手、低风险的运维产品”

这会让项目更聚焦，也更容易持续演进。

## 当前结论

现在已经可以明确归档：

- **CardPulse 主线成立**
- **AT 串口 + WSL 是当前可用主路径**
- **VoHive 只作为参考，不再是主产品方向**
- **Windows 原生驱动不是当前最优投入**
- **下一步重点是 Web 运维体验、连接状态产品化、轻量自动检测、保号视图**

换句话说，接下来不是证明“它能不能工作”，而是把它继续打磨成 **你真正愿意长期使用的本地短信运维产品**。
